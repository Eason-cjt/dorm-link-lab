应用采用四层结构，层间依赖严格单向，自上而下依次为界面层、服务层、引擎层、模型层，整体关系见图 2.1。界面层只负责渲染与收集操作，服务层负责状态编排与落盘，引擎层负责全部业务判断，模型层定义数据契约。

界面层由 ArkUI 声明式页面组成。pages/Index 用 Tabs 承载首页、规则、模拟、日志四个页签，规则编辑作为独立页面通过 router 跳转。四个视图组件（DashboardView、RuleListView、SimulatorView、LogView）不含任何业务判断，只做数据搬运与界面渲染。

服务层承担三件事：AppStore 是内存中唯一的数据源，持有规则、设备、日志、环境四份数据，并决定何时落盘；StorageService 封装 Preferences 的读写与序列化；ScenarioPresets 提供首次启动的默认规则与两组预置场景。

引擎层只有 RuleEngine 一个类，是整个应用的核心。它接收规则数组、环境快照与设备数组，返回一次完整的执行结果。这个类不 import 任何 ArkUI 或 ArkData 模块，因此可以脱离设备被单元测试直接调用，这也是 12 条测试能在本地跑起来的前提。

以「在模拟页点击执行联动」为例说明数据如何流动：SimulatorView 把四个滑块的值组装成 EnvData，连同 AppStore 中的规则数组与设备数组一起交给 RuleEngine.run()；引擎在设备副本上排序、求值、裁决冲突，返回 ExecutionResult；SimulatorView 把结果渲染到界面，同时由 AppStore 将 devicesAfter 写回设备状态、把结果追加进日志，再调用 StorageService 落盘。整个过程中业务判断全部发生在引擎层，界面层只负责数据的进出与呈现。
