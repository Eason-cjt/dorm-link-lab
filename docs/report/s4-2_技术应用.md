本项目用到的 ArkTS 与 ArkUI 能力可以归为四类，每一类都是为解决具体问题而选用的。

状态管理与页面刷新。首页、规则列表、模拟页、日志页分属四个页签，数据却在同一个 AppStore 里。由于 ArkUI 不监听对象与数组的深层变更，直接修改 rules[0].enabled 不会触发界面刷新。项目采用的方案是：子组件通过 @Prop 接收一个 dataVersion 版本号并用 @Watch 监听，父页面在页签切换、页面返回、数据落盘后把 dataVersion 加一，子组件随即重新从 AppStore 拉取数据。这个做法比给每个对象套 @Observed 简单，代价是刷新粒度较粗。

组件与布局。规则编辑页的条件与动作编辑器大量使用 Flex 换行布局做分段选择器，用 Slider 调节数值，用 Toggle 做开关，用 ForEach 渲染动态列表。选分段按钮而不是 Select 下拉，是因为手机竖屏下点击目标更大，也避免了 Select 在窄屏上的弹出层遮挡问题。

数据持久化。选用 @kit.ArkData 的 Preferences。它的语义是键值存储，put 之后必须 flush 才会真正落盘——这一点在开发初期踩过坑：只 put 不 flush，应用一被杀进程数据就丢了。四类数据分四个键存储，每次业务变更后立即 flush。

测试。使用 @ohos/hypium 编写单元测试，断言方法用 assertEqual 与 assertTrue。测试放在 src/test 目录下，属于本地单元测试，直接跑在开发机上，不需要连接设备，因此可以快速反复执行。设备端另有一个冒烟测试放在 src/ohosTest 下，用 abilityDelegatorRegistry 拉起 EntryAbility 并断言当前顶层 Ability 名称，用来验证应用能正常启动。

这几项技术并不是孤立使用的。以「执行联动」为例：Slider 收集环境值（组件），组装成 EnvData 后交给引擎（业务），引擎返回结果后页面把 devicesAfter 写回 AppStore（状态管理），再调用 Preferences 落盘（持久化），同时 dataVersion 加一让首页设备卡片刷新（状态管理）。一条链路上四类能力各司其职，缺一环用户就看不到完整效果。
