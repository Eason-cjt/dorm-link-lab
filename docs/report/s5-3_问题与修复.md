开发过程中最典型的一个问题出现在持久化环节：应用第一次重启后，日志列表能正常显示时间与场景名，但只要展开任意一条记录，界面就报错退出。

现象与定位。规则、设备、环境、日志四类领域对象在内存中是 class 实例，带有 clone()、isMultiCondition() 这类方法。落盘时用 JSON.stringify 序列化没有问题；读回来时用 JSON.parse 加类型断言，得到的只是普通对象——字段全在，但原型链是 Object.prototype，类上定义的方法一个也没有。日志展开恰好调用了结果对象上的方法，于是抛出 TypeError。ArkTS 的类型断言只在编译期起作用，运行时并不会把普通对象「变成」类实例，这一点与 TypeScript 一致，但在 ArkTS 严格模式下更容易被忽略。

尝试过的方案。第一反应是给 JSON.parse 加 reviver，在解析时把每个节点重新构造成类实例。这个方案可行，但每类对象都要写一遍 reviver，字段一改动就要同步维护，很容易漏。第二个方案是把所有方法改成静态方法——静态方法挂在类构造函数上，不依赖实例原型，反序列化出的对象可以直接调用，改动小且没有维护负担，但调用点会变成 RuleModel.isMultiCondition(rule) 这样，可读性不如 rule.isMultiCondition()。

最终采用的做法是把「复制」类操作改成自由函数（cloneDevice、cloneEnv、cloneRule），把「判断」保留为静态方法（RuleEngine.evaluate）。区分依据是所有涉及复制的地方都可能拿到反序列化对象，必须安全；而求值、条件摘要这类操作只在引擎内部使用，那里的对象都是自己 new 出来的，不存在原型缺失问题。

验证方式有两条。一是把应用杀掉进程重开，展开历史日志不再崩溃，规则、设备、环境三处数据也都能正常读写；二是在测试中补充了「引擎不修改入参设备」的用例（T12），确认副本机制在两条路径上都成立。这个问题之后，我在新增任何领域对象时都先问一句：这个对象会不会从 JSON 里还原出来？会的话就不给它挂实例方法。
