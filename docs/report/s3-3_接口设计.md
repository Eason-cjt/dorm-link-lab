表 3.2 列出了模块对外的主要接口。这些接口全部是静态方法或自由函数，不依赖组件实例，因此可以在单元测试中直接调用，不需要启动界面。

RuleEngine.run() 是最核心的接口，在模拟页点击「执行联动」时被调用。它需要三份数据：全部规则（含停用规则，引擎内部会跳过并记录原因）、一份环境快照、当前设备数组。返回值 ExecutionResult 包含五部分：触发的规则及执行顺序、设备变化明细、冲突裁决记录、未执行原因、执行后的设备快照。把「未执行原因」也作为返回值的一部分，是刻意的设计——用户排查规则不生效时，需要知道是被停用了、条件没满足，还是根本没配动作。

边界处理上，引擎对四类异常输入都有明确约定：条件数组为空的规则直接判定为不命中并记入未执行，避免空规则无条件触发；规则停用时不参与求值；条件齐备但环境不满足时同样记入未执行，原因写「环境条件未满足」；动作目标值超出设备允许区间时由 writeDeviceProperty 裁剪，不会写入非法值。

StorageService 的接口约定了一条容易被忽略的约束：loadRules 在没有历史数据时返回空数组而不是抛异常，由 AppStore 决定是否灌入默认规则。这样「首次启动」与「用户把规则删光了」两种情况能被区分开——前者灌默认值，后者尊重用户的选择。
