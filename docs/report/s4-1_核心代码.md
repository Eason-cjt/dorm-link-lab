下面这段代码是 RuleEngine.run() 的核心片段，位于 entry/src/main/ets/engine/RuleEngine.ets，对应提交 c2c58ec。它要解决的问题是：当多条规则同时命中、且对同一台设备给出不同目标值时，设备最终应该是什么状态。

```typescript
ordered.sort((a: AutomationRule, b: AutomationRule): number => {
  if (a.priority !== b.priority) {
    return a.priority - b.priority;
  }
  return a.id < b.id ? -1 : 1;
});

const applied: Map<string, AppliedRecord> = new Map<string, AppliedRecord>();
let order: number = 0;

for (let r = 0; r < ordered.length; r++) {
  const rule: AutomationRule = ordered[r];
  if (!rule.enabled) {
    RuleEngine.markSkipped(result, rule, '规则已停用');
    continue;
  }
  if (!RuleEngine.evaluate(rule, env)) {
    RuleEngine.markSkipped(result, rule, '环境条件未满足');
    continue;
  }
  order = order + 1;

  for (let a = 0; a < rule.actions.length; a++) {
    const action = rule.actions[a];
    const key = `${action.device}:${action.property}`;
    const occupied = applied.get(key);
    if (occupied !== undefined && occupied.value !== action.value) {
      result.conflicts.push(buildConflict(occupied, rule, action));
      continue;
    }
    if (occupied === undefined) {
      applied.set(key, toRecord(rule, action));
    }
    writeDeviceProperty(device, action.property, action.value);
  }
}
```

第一段是排序。规则先按 priority 升序，priority 相同时再按 ruleId 字典序。加第二级排序不是为了好看——Array.sort 对相等元素的相对顺序并不保证稳定，如果不加兜底，同一份输入可能得到不同的执行顺序，测试无法断言，日志也无法复现。补上 ruleId 之后，执行顺序完全确定。

第二段是冲突裁决。applied 是一个 Map，键是「设备:属性」，值是首次写入该属性的规则与目标值。当一条规则的动作发现该属性已被占用、且目标值不同时，直接跳过写入并生成冲突记录。这意味着先执行（优先级更高）的规则不会被后执行的规则推翻。

第三段是跳过逻辑。停用、条件不满足的规则都不抛异常、不静默丢弃，而是连同原因一起记入 skipped。这既保证引擎不会因为一条坏规则中断整轮演练，也让用户能在「未执行规则」列表里看到每条规则为何没有生效。
