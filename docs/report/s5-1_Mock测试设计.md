测试对象的选择基于一个判断：这个应用真正的业务规则集中在规则引擎里，界面与持久化更多是数据的搬运。因此测试重点放在 RuleEngine 上，通过构造不同的规则、环境与设备组合，验证条件判定、执行顺序与冲突裁决是否符合预期，而不是去测按钮点了会不会变色。

Mock 的构造方式很直接。规则引擎的入参是纯数据对象，测试中不需要模拟框架，用几个工厂函数就能拼出任意场景：makeEnv 构造一份环境快照，makeCondition 与 makeAction 分别构造条件和动作，makeRule 把它们组装成一条规则。这样每条用例只声明「输入是什么、期望什么」，不依赖界面、数据库或设备时间，也不受执行顺序影响。

三类输入的设计思路如下。正常场景选取的是应用预置业务里真实存在的规则，例如「温度 > 28℃ 开空调」「无人则关灯关空调」「光照不足且有人才补光」，验证的是主流程是否走得通。边界场景围绕阈值展开：严格大于与大于等于在等值点的差异、动作值越界后是否被裁剪到合法区间——这类问题在实际使用中最容易暴露，用户把温度调到恰好 28℃ 却发现空调不开，就是边界语义没对齐。异常场景覆盖的是「不该触发」的情况：规则没有条件、规则被停用、两条规则对同一设备给出相反指令，验证引擎不崩溃、不误触发，并且把原因如实记录下来。

另外专门设计了一条保护性用例（T12），验证引擎不会修改调用方传入的设备数组。这条用例的价值不在于覆盖率，而在于它锁住了一个设计约束——只要有人把引擎改成直接操作入参，这条用例立刻会失败。
