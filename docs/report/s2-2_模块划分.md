表 2.1 列出了本项目的 6 个模块及其接口关系。由于本项目独立完成，没有跨成员分工，这张表的作用是明确代码内部的分层边界：界面层不得直接操作持久化，引擎层不得反向依赖界面。

各模块的协作可以用一次「新增规则并立即生效」来说明。用户在 RuleEditPage 中录入条件与动作，页面把编辑结果组装成 AutomationRule 对象交给 AppStore；AppStore 先按 id 判断是新增还是修改，再调用 StorageService.saveRules 把整个规则数组序列化写入 Preferences；随后页面返回。Index 的 onPageShow 在返回时被触发，dataVersion 自增，RuleListView 通过 @Watch 监听到变化，重新从 AppStore 拉取规则数组，界面于是显示出新规则。整个过程中规则对象只在服务层与模型层之间传递，界面层拿到的一直是副本。

第二处值得说明的衔接是「执行联动」。SimulatorView 调用 RuleEngine.run() 后拿到 ExecutionResult，其中 devicesAfter 是引擎在副本上推演出的结果。页面需要把它写回 AppStore.devices，再调用 persistDevices 落盘。这里刻意让引擎不直接修改 AppStore，是因为引擎必须是纯函数：入参不可变，才能保证同样的输入得到同样的输出，也才能让测试用例直接断言结果而不必清理全局状态。接口传递的数据也因此非常明确——进去的是规则、环境、设备三份只读数据，出来的是含五类信息的执行结果。
