这个项目让我对 HarmonyOS 的 Preferences 有了比较具体的认识，也看清了它的边界在哪里。

用途方面，Preferences 适合「整存整取、没有查询需求」的小体量配置数据。本项目的规则、设备状态、环境参数都属于这一类：数量小、每次改动都是整体覆盖、读取时一次全部取出。用它的好处是 API 极简，get、put、flush 三个动作就能完成持久化，不需要建表、写 SQL、管理连接。对课程作业这种规模，它比 RDB 快得多，出错面也小。但有一个必须记住的点：put 之后不 flush 只是写进内存缓存，进程被杀就丢了，我最初的日志功能就是因为漏了 flush 而出现过数据丢失。

局限方面，最直接的是单个 value 有长度上限（约 8KB），超出后写入失败。我在日志功能上撞过这堵墙：一开始把整条执行结果连同设备快照一起存，几条之后就写不进去了，而且失败时没有明显报错，只能从「重启后数据消失」这个现象反推。其次是 Preferences 没有查询能力，只能按 key 整体读写，想做「查最近三天所有冲突记录」这种筛选，必须全部读出来在内存里过滤。第三是它没有事务，多份数据之间的一致性要自己保证——我把四类数据分四个 key 存，某个 key 写成功、另一个失败时就会出现不一致，只是当前写入频率低、数据量小，这个风险还没有暴露。

如果这个应用要继续做下去，日志部分应该换成 RDB：建一张执行记录主表，设备变化、冲突、未执行规则各自建子表，按时间与设备类型建索引，既能长期保存历史，也能支持条件检索。规则本身可以继续留在 Preferences 里，因为它就是典型的整体读写形态，换成数据库反而是过度设计。

核查技术资料的方式，我形成了三步习惯。遇到不确定的 API，先看 DevEco Studio 里的代码提示并跳转到定义，确认方法签名和参数类型；再看华为开发者联盟的官方文档，重点读「接口说明」和「约束与限制」两节，很多坑就写在那里，Preferences 的单值上限我就是这样查到的；如果文档描述不清，直接去看 SDK 里的 d.ts 声明文件，它比文档更准确。这次遇到的反序列化问题，最终是靠 d.ts 里的类型声明配合运行时抛出 TypeError 的实际调用栈定位的，光看文档反而绕了远路。

接下来要学的东西有三个具体方向。第一是 RDB 与关系型数据建模，包括建表、索引、事务与游标查询，目标是把日志模块改成支持检索的版本。第二是 ArkUI 的状态管理新方案，@ObservedV2 与 @Trace 相比我现在用的 @State/@Prop/@Watch 粒度更细，能省掉为了触发刷新而做的整体替换和版本号自增这类手工操作。第三是一次开发多端部署，把当前只适配手机竖屏的布局扩展到平板与 2in1 设备。对应的资料路径是华为开发者联盟的「应用开发」文档与最佳实践、DevEco Studio 自带的 Sample 工程，以及 OpenHarmony 仓库里 ArkUI 组件与状态管理的源码。

这次独立完成一个大作业，最大的收获不是写完了某个功能，而是意识到「能跑」和「可靠」是两件事。功能写完只花了两天，而让它不丢数据、不乱序、重启能恢复、坏了能查出来，花的时间差不多一样多。
